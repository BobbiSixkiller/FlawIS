# BPF 2026 prototype coverage

Audit date: 2026-11-17. FlawIS baseline: `81fd98b3` (clean working tree before this documentation audit).

**At the audited baseline, FlawIS did not cover the complete prototype workflow.** Submission/reviewer management, private review links, questionnaires, document history and basic correction requests exist. The largest gaps concern structured correction rounds, final author proof approval and editorial delivery. There are also material differences in acceptance rules and template compatibility.

This is a source-based comparison, not an approved implementation plan or a claim about the currently deployed staging/production version. “Supported” means implementation exists; it does not mean the BPF conference has already been configured with the required form and templates.

The matrix records the November 17 baseline. The subsequent BPF implementation and its template checks, correction receipts, proof and publication steps are documented in the [coordinator workflow](conference-reviews.md#coordinator-workflow).

## Source and comparison method

The supplied folder is `Downloads/BPF_2026_Podklady_pre_IT`. Its technical handover is dated **16 November 2026**. The package contains the technical guide, section rules, communication templates, a synthetic `DEMO-01` lifecycle, DOCX examples, a sample publication ZIP, and source copies of `evidencia` and `portal`.

The technical guide cites reference revisions `bb8ad34` and `d214cc2`. These are the guide's provenance claims: the distributed source copy has no Git history and contains generalized demo identifiers. This audit compares the actual supplied files, rather than assuming the reference live sites and sanitized copy are identical.

Prototype paths below are relative to `03_Zdrojovy_kod/evidencia/`, unless prefixed with `portal/`. FlawIS links point into this repository. The technical guide's lifecycle, acceptance scenarios, rules and synthetic scenario were crosschecked against source implementations. Deployment advice, proposed faculty SSO and institution-specific operating arrangements are not counted as already-prototyped application features.

The [earlier chat comparison](reviews-chat-crosscheck.md) remains a historical record. This package resolves its uncertainty about “two versions”: **a clean DOCX and a DOCX with tracked changes**, not two language variants.

## Findings that change the implementation priorities

### Acceptance is currently less restrictive than the prototype

This is an executable rule difference, not just missing UI. `ReviewService.action("DECIDE")` counts submitted non-author reports and checks for outstanding revision requests. It does not inspect whether a submitted recommendation is negative. A conditional report with no revision request also does not itself create a blocker. New manuscript uploads reset formal approval, but the acceptance predicate does not recheck that flag either. The prototype's `validateArticle` checks formal requirements, negative recommendations, conditional corrections and report closure.

Do not describe current “all reports complete” gating as implementation of the BPF acceptance policy. If BPF parity is desired, decide the configurable policy for negative/conditional reports and authorized exceptions before extending the shared state model. No live decision was submitted during this audit.

### The supplied official review DOCX cannot be uploaded unchanged

The package's `01_Pravidla_a_sablony/02_BPF_2026_Formular_recenzneho_posudku_EN_A4.docx` contains `{{SECTION}}`, `{{ARTICLE_ID}}`, `{{TITLE}}` and `{{REVIEWER_NAME}}`. A read-only local parse with the installed FlawIS `Docxtemplater`/`PizZip` and the current upload options rejected it with duplicate opening/closing tag errors.

FlawIS uses single-brace placeholders such as `{paper}`, `{reviewer}`, `{recommendation}`, `{answers}` and `{answer_FIELD_ID}`. Section/article-code placeholders are not currently supplied. The prototype also has a specialized renderer for its rating boxes. Merely uploading that Word, or merely replacing braces, is insufficient to reproduce the full mapping. The manuscript template has no templating placeholders and is a separate author-download asset; its formatting is not validated against BPF rules by FlawIS.

The recent template-management implementation is still useful: it provides the upload/download and report-generation infrastructure. What remains is adapting/configuring the BPF questionnaire and template, including any required new data mappings and conditional validation.

## Recommended sequence if implementation is requested

1. Agree and enforce acceptance/formal-check policy, including negative and conditional recommendations; adapt the BPF form/template and required metadata mappings.
2. Extend correction requests with formal/post-review type, paired files, per-point responses/checks and linked follow-up rounds. Add the coordinator's request-bound external receipt operation.
3. Add manuscript comparison and the separate targeted reviewer correction check, preserving original reports and document bindings.
4. Add version-specific final author proof, approval/no-response states, then publication-package verification and actual handoff records.
5. Build publication ZIP/XLSX and ordered Word assembly on those approved final versions.
6. Address coordinator convenience: unread activity/priority queue, returned-report matching, grouped/external-email dispatch if staff still need that workflow.

Automatic anonymization is a separate optional aid alongside the existing manual route; retain explicit human approval. Do not carry over the prototype's special `DEMO-CONFLICT`, `DEMO-PARALLEL` or `DEMO-ABSTRACT` branches as production rules. Generalize any approved exceptions.

The prototype also includes a scoped-coordinator convenience that parses an author's reviewer nominations from specially formatted notes (`lib/reviewer-nominations.ts`, `app/dashboard.tsx:309`). No equivalent nomination/prefill flow was found in FlawIS. Treat that limited convention as a separate product choice, not evidence of a general author-nomination portal.

## Architecture and validation limits

FlawIS already supplies its own accounts, conference/section authorization, MongoDB/MinIO persistence, protected downloads, audit trail and durable notification delivery. Reproducing Cloudflare D1/R2, a Sites identity bridge or a second Worker is not necessary for functional parity. The public endpoints differ too: the prototype uses URL-fragment tokens and a separate gateway; FlawIS uses private token routes with no-referrer metadata and authorization in core. This audit does not claim those architectures are identical or constitute a full security review.

Read during this audit: the package guides, scenario, relevant prototype libraries/routes/UI, DOCX XML and sample ZIP member list; FlawIS models, services, routes, coordinator/author/reviewer UI and relevant test assertions. Broad source searches across `core/src`, `client/src` and `mail/src` also checked for final proof, publication approval/delivery, proceedings merging, tracked revision pairs, follow-up items and unread review activity beyond the obvious files, excluding generated contracts and locale dictionaries. Missing-feature findings mean no counterpart was found in this inspected baseline. Decisive helper evidence was checked against source; a separate scoped factual check confirmed the acceptance, upload-binding, questionnaire and correction-check findings.

Executed: a local, read-only compatibility parse of the supplied review template; documentation drift, local-link and whitespace checks. No prototype installation/build, application unit/integration/browser suite, database inspection/import, real email, workflow mutation or deployment was performed. Existing test assertions are evidence of intended coverage, not freshly executed test results. The supplied guide's claimed 65 internal/15 portal test passes were not rerun or independently confirmed.

Only this comparison, its documentation reference and the temporary audit plan were changed. The identified feature gaps remain documented here; this audit does not silently authorize their implementation.
